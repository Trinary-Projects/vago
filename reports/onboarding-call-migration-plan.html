Onboarding Call → Vago: Deep Comparison & Migration Plan

A component-by-component comparison of Disha's Python bots/onboarding_call/ bot against the current Vago (talk-go) codebase, and a phased plan to port it as the third bot type alongside sales_call and follow_up.

Date: 2026-07-06 Python ref: disha-backend @ bots/onboarding_call/ Go ref: vago @ main (e1b9055) Predecessor plans: disha-integration-plan.md, sales-call-drop-in-report.html

Verdict: roughly 60% of onboarding's machinery already exists in Vago. The real work is the stage machine.

Because sales and follow-up were ported first, most of onboarding's shared modules already have Go equivalents — several were literally ported from bots/onboarding_call/ (phonetic text filter, LLM response timeout, lazy Soniox connect, sound mixer, tool-chunk resume reordering, chunk persistence shape). The genuinely new work is the onboarding-specific stage complex: variant config, ConversationState, staged prompt compilation, the update_stage tool + StageManager, deep thinking, careplan detection, the stage-threshold reminder processor, per-chunk conversation-state S3 uploads, onboarding post-call fields, and (variant-gated) the stage-transition tracker with fuzzy matching. Three small core-surface extensions are needed and require design sign-off per AGENTS.md before implementation (§5).

1. Scope & method

Two parallel deep-reads were done: (a) every file in disha-backend/bots/onboarding_call/ plus its launch path (bot_worker_manager.py, bot_session_manager.py, gke_pod_manager.py, post-call manager) and shared services; (b) the full Vago tree — disha/, voicepipelinecore/ (incl. llmrouter/), internal/worker/ — with explicit checks for absences (stage machinery, recording, backchannel audio, Krisp, Smallest STT). Two load-bearing core facts were verified directly in source: aggregatorSharedState (aggregator_shared_state.go) has no system-message replacement method, and LLMProcessor.RegisterTool (llm_processor.go:97) is append-or-replace but unlocked — safe at build time, racy if called mid-call while runLLM copies p.tools.

Status legend used throughout: Ready exists in Vago, reuse as-is · Extend exists but needs modification · New must be built · Verify needs a fact check before/while building · Design architectural change, discuss before implementing · Skip intentionally not ported.

2. Python onboarding architecture at a glance

Routing: BotWorkerManager.run_bot_with_monitoring treats onboarding as the default bot type (anything that isn't follow_up / sales_call / post_plan_call runs onboarding_call_daily.run_bot). BotWorkerType includes onboarding_call explicitly, and Vago's create_worker_room already receives bot_worker_type, so the Go side routes cleanly through disha.NewBot("onboarding_call").

Pipeline (Python, base_pipeline_manager.py)

transport.input() → rtvi → stt → context_aggregator.user()
  → [StageThresholdProcessor]            # non-tracker variants only
  → llm → LLMResponseTimeoutProcessor(7s) → LLMOutputFilter()
  → tts → transport.output() → context_aggregator.assistant()

Notable vs sales/follow-up: no talk-time monitor (that is sales-only), LLMOutputFilter present (like follow-up), same 7s idle prompt + 120s pipeline idle watchdog, same greet-first kickoff, same lazy Soniox connect via STTConnectFrame, same Cartesia sonic-3 Hindi voice 95d51f79-… (identical to Vago's hardcoded voice), same office-sound output mixer.

The onboarding-specific brain

  • Variant config — user_profile.onboarding_call_variant selects document OB_Call_Configs/{variant}_config → Config{model, main_system_prompt, careplan_switcher_prompt, careplan_switcher_stage_name, start_stage, common_stages[], care_plans[], recording_enabled_percentage}. Each StageConfig has {name, prompt, next_stages[], deep_thinking[], is_end_stage, turn_threshold}. Variant missing → Python forces legacy variant "student" with resume disabled.
  • ConversationState — {variant, current_stage, selected_care_plan, variable_store, stage_turn_count, threshold flags}. Serialized to S3 per user/assistant chunk as conversation_state/{conversation_id}/{chunk_id}.json (US bucket) and referenced by the chunk's conversation_state_s3_key. This is also the resume source.
  • Prompt compilation (prompt_parser.py) — fetch the current stage's prompt with {profile_variables + variable_store}, inject the result as analysis into the main system prompt along with patient_info and IST current_datetime. On every stage transition the system message is replaced in-place and the update_stage tool's enum is refreshed to current_stage.next_stages.
  • Stage transitions — two architectures by variant:
    • Tool-call variants (default): LLM calls update_stage(next_stage); the handler speaks a "hmm..." filler if the LLM produced no text alongside the tool call, runs StageManager.process_transition, and decides run_llm from "had no text OR a new user message arrived mid-transition".
    • Tracker variants (student_test, misc1): no update_stage tool. After every completed LLM call, a background tracker runs a rapidfuzz matcher over the assistant's last utterance against each next-stage's trigger_statements; yes → transition directly, maybe → small LLM classifier (obcall_helpers/agenda_tracker/* prompts, gemini-flash-lite failover config, 32 max tokens), no → skip.
  • StageManager.process_transition — careplan detection when entering the switcher stage, stage resolution, blocking deep thinking, advance_stage + recompile/apply prompt, non-blocking deep thinking (recompile again on completion), RTVI "Agenda changed" messages, debug-log chunk + assistant tool_calls chunk + tool result chunk (the resume-replay trio), analytics job CallAgendaUpdate-{stage}, and a stage-transition timing log.
  • Deep thinking (deep_thinking_manager.py) — per-stage LLM analysis calls (transcript + patient profile against a doc-store prompt), blocking ones gate the prompt compile, non-blocking merge into variable_store later. Model: gpt_oss120_fast_hedged (Cerebras hedged with OpenRouter at 1s), temp 0.7, max 4000 tokens, JSON output merged into variable_store; result persisted as an assistant debug-log chunk.
  • Careplan (careplan_manager.py) — on entering the switcher stage with no plan: LLM classify (careplan_switcher_prompt, gpt-oss120-fast) → JSON {"selected_care_plan": name}, fallback "general"; activate unlocks that plan's stages and calls POST /bot/set_user_careplan.
  • Stage threshold (stage_threshold_processor.py) — counts assistant turns per stage; over turn_threshold injects a <system_instruction> reminder into the next LLM context; over threshold+3 fires Sentry + RTVI + POST /bot/add_tag_to_user ("Stage Transition Failure").
  • Post-call — run_post_call_operations carries onboarding_call_done (= user duration > 0 AND current stage is_end_stage), latest_onboarding_call_stage, diet/fitness_plan_intensity_level (from variable_store), and conversation_variables (the whole variable store). The server side branches on these for onboarding-done jobs / incomplete-call retry scheduling.
  • Resume — bot_session_manager only selects a resume chunk if it has a conversation_state_s3_key; init loads that JSON → ConversationState.from_resume, replays chunks (incl. tool pairs, reordered), and injects an onboarding-specific <system_instruction> resume nudge (<5 min: continue naturally "hanji to aap keh rhe the…"-style; older: acknowledge disconnection and recap).

5. Core design decisions needing discussion first

Per AGENTS.md, these touch frame semantics / shared surfaces / new processors — each needs a short design note (existing pattern, minimal change, alternatives, tests) agreed before implementation. Recommendations included.

D1 — Mid-call system-message replacement + tool-enum refresh

Problem: every stage transition replaces the system message (compile_and_apply) and swaps the update_stage enum. Verified: aggregatorSharedState has no replacement method (only initial-message seeding), and LLMProcessor.RegisterTool mutates p.tools/p.toolMap without a lock while runLLM copies p.tools on another goroutine — mid-call re-registration is a data race today.

Recommendation: the minimal change is (a) an exported, mutex-guarded ReplaceSystemMessage(text string) on ContextAggregatorPair (state already has mu); (b) a small mutex around LLMProcessor tool registration + the runLLM snapshot so RegisterTool becomes safe mid-call (re-registration already replaces by name). No new frame types; the transition runs inside a tool handler, which executes before the next LLM run, so ordering is naturally safe for tool-call variants. Tracker variants transition from a background goroutine — the same mutexes cover it, with the "stale result" lock (D3) providing the ordering guard Python gets from its asyncio lock.

D2 — Tool-handler context: "did the LLM speak?", "did the user speak mid-transition?", filler injection

Problem: the update_stage handler needs three things Vago's ToolCallRequest doesn't carry: whether the assistant produced text alongside the tool call (decides both the "hmm..." filler and run_llm), whether a new user message landed during the transition (also feeds run_llm), and a way to push a TTSSpeakFrame from inside a handler.

Recommendation: extend ToolCallRequest with a ResponseHadText bool field populated by LLMProcessor (it already tracks streamed content for llm_call_result) — a field on an existing type, not a new frame. For the filler, let the handler use the existing TTSSpeakFrame path — expose a narrow Speak(text) on the processor or hand the handler a push closure; matches Pipecat's handlers pushing TTSSpeakFrame. For "new user message mid-transition", the cheapest faithful check is asking the aggregator pair whether the last message role is user at handler-exit (state is already shared + mutexed). Alternatives (a full FunctionCallParams-style context object) are more surface than needed.

D3 — LLM-call-completed hook (tracker variants only)

Problem: the transition tracker consumes on_llm_call_complete(assistant_response, is_interrupted) — the generated response, not the played text, so OnAssistantTurnCommitted is the wrong hook. Vago has no LLM-completion callback (only the RTVI llm_call_result event).

Recommendation: if launch variants don't include student_test/misc1, defer entirely (phase 7). If needed: one optional callback on CallEvents (OnLLMCallCompleted(text string, interrupted bool)) — it's a lifecycle/turn event, which is exactly what CallEvents is for; no new frame, no new dispatcher.

D4 — Deep-thinking model strategy: drop hedging

Problem: Python hedges Cerebras against OpenRouter at 1s. Vago's router has no hedged execution, and the established precedent (follow-up get_guidance) is: no in-call failover, single health-selected call from gpt-oss120-fast, Sentry capture on failure/empty (except ctx cancellation).

Recommendation: reuse the get_guidance pattern verbatim (fresh one-shot client, timeout, Sentry tag disha_onboarding/deep_thinking). A blocking-DT failure should degrade to "transition without new variables" — Python effectively does the same when a DT returns garbage. This avoids building hedged execution into the router for one caller.

D5 — StageThresholdProcessor placement

Problem: a new processor between user aggregator and LLM. AGENTS.md says new processors are architectural changes.

Recommendation: mirror the accepted LLMResponseTimeoutProcessor/LLMOutputFilterProcessor precedent: a narrow stream processor in voicepipelinecore that counts turns and mutates the outgoing LLMMessagesFrame, with all policy (threshold value, reminder text, Sentry/tagging callbacks) injected by the bot at construction. Core stays business-free; onboarding wires it, sales/follow-up don't.

Everything else needs no core change. StageManager, DeepThinking, CarePlan, config, state, resume, S3 state upload, new API methods, debug chunks — all live in disha/, using surfaces that already exist (Redis client, API client, DocumentStore, Jinja renderer, S3 uploader, UIEvents, tool registration, CallEvents).

6. Migration plan — phases

Sequenced so each phase builds and tests green (go test -race ./...) before the next; behavior is exercisable end-to-end from phase 3 onward via the local browser client with a real variant config. No commits without explicit review, per project rules.

recon · small

Phase 0 — Recon & decisions

  • Dump the live variant configs (OB_Call_Configs/onboarding_call_release_config + each {variant}_config) from staging Redis/doc store: which variants are live, what model group each uses, stage graphs, deep-thinking prompts, turn_thresholds, recording_enabled_percentage.
  • Answer §8 questions (launch variants → tracker in/out of scope; DT hedging; recording start point; idle-cap parity).
  • Verify enqueue-job callables for stage-transition logs + analytics events (module path, queue, kwargs, unbound-safe).
  • Write the D1–D5 design notes and get sign-off.

Exit: scoped variant list, confirmed model groups, approved design notes.

mechanical · medium

Phase 1 — Types & plumbing (no behavior)

  • disha/onboarding_config.go: config structs + ConfigManager port (resolution order, prompt-config collection) + tests against captured real config JSON.
  • disha/onboarding_state.go: ConversationState (mutexed) + persist-dict JSON + from_resume + intensity/variable extraction + tests.
  • APIClient.SetUserCareplan / AddTagToUser with enqueue fallback + httptest coverage.
  • US-bucket JSON PUT in the S3 uploader; UserProfileData.onboarding_call_variant; llmrouter group additions from phase 0 findings.

Exit: all new types round-trip real staging config/state JSON in tests.

core · small, design-gated

Phase 2 — Core surface extensions (D1, D2, D5; D3 only if tracker in scope)

  • ContextAggregatorPair.ReplaceSystemMessage; mutex tool registration in LLMProcessor + safe mid-call re-registration test (race detector).
  • ToolCallRequest.ResponseHadText + handler speak path + last-message-role query.
  • Generic StageThresholdProcessor (callback-injected policy) + processor tests in the Pipecat-parity harness.
  • (If needed) CallEvents.OnLLMCallCompleted.

Exit: go test -race green including new concurrency tests; AGENTS.md updated with the decided surfaces.

bot · medium

Phase 3 — OnboardingCallBot skeleton (callable end-to-end, single stage)

  • disha/onboarding_call.go: plan() (startup, variant/config load, prompt compile, fresh initial messages [system, user:"hello?"]), BuildTask() (pipeline wiring incl. output filter + threshold slot, no talk-time), NewBot registration.
  • end_call tool wiring; prompt metadata (system + stage prompt identity + exact variables) on every conversation LLM call.
  • Local smoke: browser call through /bot/create_worker_room with a real staging variant config against local Redis — bot greets from the start stage.

Exit: a full local call on the start-stage prompt, chunks persisted with current_agenda, debug log uploaded.

bot · large

Phase 4 — Stage machine

  • disha/onboarding_stage_manager.go: process_transition (resolution, advance, recompile/apply, enum refresh, RTVI messages, Sentry paths).
  • update_stage handler: end_call special case, "hmm..." filler, run_llm logic.
  • Persistence trio (debug chunk + assistant tool_calls chunk + tool result chunk), analytics + timing-log enqueues.
  • Threshold processor wiring (turn counts from state, reminder text, tag/Sentry at +3).
  • Tests: transition happy path, invalid stage, redundant transition, threshold reminder injection, chunk shapes byte-compared to Python fixtures.
