Onboarding Call → Vago: Deep Comparison & Migration Plan

A component-by-component comparison of Disha's Python bots/onboarding_call/ bot against the current Vago (talk-go) codebase, and a phased plan to port it as the third bot type alongside sales_call and follow_up.

Date: 2026-07-06 Rev 3: tracker default · D1/D3 approved · hedging in scope Python ref: disha-backend @ bots/onboarding_call/ Go ref: vago @ main (e1b9055) Predecessor plans: disha-integration-plan.md, sales-call-drop-in-report.html

Verdict: roughly 60% of onboarding's machinery already exists in Vago. The real work is the stage machine.

Because sales and follow-up were ported first, most of onboarding's shared modules already have Go equivalents — several were literally ported from bots/onboarding_call/ (phonetic text filter, LLM response timeout, lazy Soniox connect, sound mixer, tool-chunk resume reordering, chunk persistence shape). The genuinely new work is the onboarding-specific stage complex: variant config, ConversationState, staged prompt compilation, the StageManager driven by the background stage-transition tracker with fuzzy matching, deep thinking, careplan detection, per-chunk conversation-state S3 uploads, and onboarding post-call fields. Two small core-surface extensions are needed and require design sign-off per AGENTS.md before implementation (§5).

* Decision (Jaideep, 2026-07-06): the stage-transition tracker is the default architecture for all variants going forward. The update_stage tool-call path is not ported — no update_stage tool, no tool-handler filler/run_llm logic, and no StageThresholdProcessor (Python wires it only for tool-call variants). This drops former design items D2 and D5 and makes the tracker (former optional phase 7) core scope. Same-day follow-ups: D1 and D3 are approved as specified; every stage prompt's config_json can be assumed to carry trigger_statements; and hedged background-LLM execution is IN scope (D4 reversed) — a reusable "background call must respond fast" primitive with Python-exact semantics (closed same day, §5 D4); get_guidance is a confirmed later adopter. All plan decisions are now closed; only the D4 Go interface shape remains as a design-note artifact.

1. Scope & method

Two parallel deep-reads were done: (a) every file in disha-backend/bots/onboarding_call/ plus its launch path (bot_worker_manager.py, bot_session_manager.py, gke_pod_manager.py, post-call manager) and shared services; (b) the full Vago tree — disha/, voicepipelinecore/ (incl. llmrouter/), internal/worker/ — with explicit checks for absences (stage machinery, recording, backchannel audio, Krisp, Smallest STT). Two load-bearing core facts were verified directly in source: aggregatorSharedState (aggregator_shared_state.go) has no system-message replacement method, and LLMProcessor.RegisterTool (llm_processor.go:97) is append-or-replace but unlocked — safe at build time, racy if called mid-call while runLLM copies p.tools.

Status legend used throughout: Ready exists in Vago, reuse as-is · Extend exists but needs modification · New must be built · Verify needs a fact check before/while building · Design architectural change, discuss before implementing · Skip intentionally not ported.

2. Python onboarding architecture at a glance

Routing: BotWorkerManager.run_bot_with_monitoring treats onboarding as the default bot type (anything that isn't follow_up / sales_call / post_plan_call runs onboarding_call_daily.run_bot). BotWorkerType includes onboarding_call explicitly, and Vago's create_worker_room already receives bot_worker_type, so the Go side routes cleanly through disha.NewBot("onboarding_call").

Pipeline (Python, base_pipeline_manager.py)

transport.input() → rtvi → stt → context_aggregator.user()
  → [StageThresholdProcessor]            # tool-call variants only — NOT in the Go pipeline*
  → llm → LLMResponseTimeoutProcessor(7s) → LLMOutputFilter()
  → tts → transport.output() → context_aggregator.assistant()

Notable vs sales/follow-up: no talk-time monitor (that is sales-only), LLMOutputFilter present (like follow-up), same 7s idle prompt + 120s pipeline idle watchdog, same greet-first kickoff, same lazy Soniox connect via STTConnectFrame, same Cartesia sonic-3 Hindi voice 95d51f79-… (identical to Vago's hardcoded voice), same office-sound output mixer.

The onboarding-specific brain

  • Variant config — user_profile.onboarding_call_variant selects document OB_Call_Configs/{variant}_config → Config{model, main_system_prompt, careplan_switcher_prompt, careplan_switcher_stage_name, start_stage, common_stages[], care_plans[], recording_enabled_percentage}. Each StageConfig has {name, prompt, next_stages[], deep_thinking[], is_end_stage, turn_threshold}. Variant missing → Python forces legacy variant "student" with resume disabled.
  • ConversationState — {variant, current_stage, selected_care_plan, variable_store, stage_turn_count, threshold flags}. Serialized to S3 per user/assistant chunk as conversation_state/{conversation_id}/{chunk_id}.json (US bucket) and referenced by the chunk's conversation_state_s3_key. This is also the resume source.
  • Prompt compilation (prompt_parser.py) — fetch the current stage's prompt with {profile_variables + variable_store}, inject the result as analysis into the main system prompt along with patient_info and IST current_datetime. On every stage transition the system message is replaced in-place and the update_stage tool's enum is refreshed to current_stage.next_stages.
  • Stage transitions — Python has two architectures by variant; per the 2026-07-06 decision, the Go port implements only the tracker*:
    • Tracker (the Go path, and the new default for all variants) — today live on student_test/misc1: no update_stage tool (the LLM's only tool is end_call). After every completed LLM call, a background tracker runs a rapidfuzz matcher over the assistant's last utterance against each next-stage's trigger_statements (from the stage prompt's config_json); yes → transition directly, maybe → small LLM classifier (obcall_helpers/agenda_tracker/* prompts, gemini-flash-lite failover config, 32 max tokens), no → skip. Stale results are dropped under a lock if the stage changed mid-flight; stages named *closing* or with no next_stages are skipped.
    • Tool-call variants (NOT ported — reference only): LLM calls update_stage(next_stage); the handler speaks a "hmm..." filler when the LLM produced no text, and decides run_llm from "had no text OR a new user message arrived mid-transition". Also brings the StageThresholdProcessor ("you seem to have skipped the stage transition" reminders). All of this exists only to make the tool-call architecture work and is skipped.
  • StageManager.process_transition — careplan detection when entering the switcher stage, stage resolution, blocking deep thinking, advance_stage + recompile/apply prompt, non-blocking deep thinking (recompile again on completion), RTVI "Agenda changed" messages, a debug-log chunk (Agenda changed(Stage Transition Tracker) from X => Y, additional_data.tool_call_id = stage_transition_tracker_{uuid}), analytics job CallAgendaUpdate-{stage}, and a stage-transition timing log. The assistant-tool_calls-chunk + tool-result-chunk pair is written only for tool_call source in Python, so the Go tracker path writes just the debug chunk — the existing tool-pair replay infra still covers end_call/follow-up chunks.
  • Deep thinking (deep_thinking_manager.py) — per-stage LLM analysis calls (transcript + patient profile against a doc-store prompt), blocking ones gate the prompt compile, non-blocking merge into variable_store later. Model: gpt_oss120_fast_hedged (Cerebras hedged with OpenRouter at 1s), temp 0.7, max 4000 tokens, JSON output merged into variable_store; result persisted as an assistant debug-log chunk.
  • Careplan (careplan_manager.py) — on entering the switcher stage with no plan: LLM classify (careplan_switcher_prompt, gpt-oss120-fast) → JSON {"selected_care_plan": name}, fallback "general"; activate unlocks that plan's stages and calls POST /bot/set_user_careplan.
  • Stage threshold (stage_threshold_processor.py) — counts assistant turns per stage; over turn_threshold injects a <system_instruction> reminder into the next LLM context; over threshold+3 fires Sentry + RTVI + POST /bot/add_tag_to_user ("Stage Transition Failure").
  • Post-call — run_post_call_operations carries onboarding_call_done (= user duration > 0 AND current stage is_end_stage), latest_onboarding_call_stage, diet/fitness_plan_intensity_level (from variable_store), and conversation_variables (the whole variable store). The server side branches on these for onboarding-done jobs / incomplete-call retry scheduling.
  • Resume — bot_session_manager only selects a resume chunk if it has a conversation_state_s3_key; init loads that JSON → ConversationState.from_resume, replays chunks (incl. tool pairs, reordered), and injects an onboarding-specific <system_instruction> resume nudge (<5 min: continue naturally "hanji to aap keh rhe the…"-style; older: acknowledge disconnection and recap).

5. Core design decisions needing discussion first

Per AGENTS.md, these touch shared surfaces and needed sign-off before implementation. Status after the 2026-07-06 review: D1 and D3 are approved as specified below; D4's direction is approved (hedging in scope) with the interface to be settled in its design note; D2 and D5 are dropped.

D1 — Mid-call system-message replacement Approved

Problem: every stage transition replaces the system message (compile_and_apply). Verified: aggregatorSharedState has no replacement method (only initial-message seeding).

Recommendation: an exported, mutex-guarded ReplaceSystemMessage(text string) on ContextAggregatorPair (state already has mu). No new frame types. Scope reduction from rev 1: with the tracker default there is no update_stage tool, so the tool set is static (end_call only) and the mid-call tool re-registration race in LLMProcessor.RegisterTool no longer needs fixing for this port (worth a defensive mutex someday, but not on this critical path). Transitions run from the tracker's background goroutine; the shared-state mutex plus the tracker's stale-result lock (D3 consumer side) provide the ordering guard Python gets from its asyncio lock.

D2 — Dropped Tool-handler context (filler / run_llm logic)

Existed only to serve the update_stage handler ("hmm..." filler, run_llm decision, mid-transition user-message check). With the tracker-default decision the tool-call path is not ported, so no ToolCallRequest extension, no handler speak path, and no last-message-role query are needed. Kept here so the scope cut is visible.

D3 — LLM-call-completed hook (now required) Approved

Problem: the transition tracker consumes on_llm_call_complete(assistant_response, is_interrupted) — the generated response, not the played text, so OnAssistantTurnCommitted is the wrong hook. Vago has no LLM-completion callback (only the RTVI llm_call_result event). With tracker as the default architecture this is mandatory, not variant-gated.

Recommendation: one optional callback on CallEvents (OnLLMCallCompleted(text string, interrupted bool)) fired by LLMProcessor where it already emits llm_call_result — it's a lifecycle/turn event, which is exactly what CallEvents is for; no new frame, no new dispatcher.

D4 — Hedged background-LLM execution Approved — semantics closed 2026-07-06

Decision (Jaideep, 2026-07-06): hedging IS needed — build something logically equivalent to Python's hedged failover, not necessarily interface-identical. Design it as a reusable primitive for the general case of "a background process must respond quickly so the model can move forward" — deep thinking is the first consumer, get_guidance is a confirmed later adopter (see supersession note), and more such background-assist calls are expected.

Shape: two layers, both in llmrouter (the sub-package already allowed to own HTTP/provider concerns — this never touches voicepipelinecore proper): a generic hedge helper (plain goroutines + select, no frames, no pipeline involvement) and a hedged one-shot completion mode over a fixed ordered primary/hedge endpoint pair (Python selects config_list[0]/[1] directly — Cerebras then OpenRouter-throughput-sorted — not health-ranked), reusing the existing per-provider request shaping and exposed behind the same one-shot client interface get_guidance uses today so adoption is a constructor swap. Only the exact Go interface remains for the design note.

Confirmed semantics (verified against services/llm_failover_service.py:308-484, generate_with_hedged_request):

  • Hedge trigger — Python-exact: whole-call elapsed time; wait up to hedge_threshold_ms (default 1000ms) for the primary to complete (no first-byte special-casing).
  • Primary errors before the threshold → fire the hedge immediately and return its result (sequential fallback, no race).
  • Threshold hit → fire the hedge in parallel; the primary is not cancelled at the threshold. First successful finisher wins and the slower attempt is then ctx-cancelled; if the first finisher failed, await the other instead.
  • Blacklisting: a slow loser is never blacklisted (it's merely cancelled — slow-but-healthy is what hedging exists for). An attempt that completes with a genuine transient error blacklists its config exactly per Python's classification (rate-limit, auth/404-class, timeouts, 5xx, empty choices — _invoke_llm_for_config).
  • Logging — exact Python parity: every attempt that completes (success or error) logs through the standard LLM logging path (Go: the existing LogSink → log_llm_call_job enqueue) with its own usecase type — i.e., when the hedge fires and both complete, both calls are logged. An attempt cancelled mid-flight never reaches logging, matching Python's cancelled asyncio task. No winner-only special-casing.
  • Cancellation contract: parent-ctx cancellation (barge-in/EndFrame) cancels both attempts and is never treated as an endpoint error, matching the existing router rule.

Supersession resolved: get_guidance WILL adopt this primitive, but later — after it has soaked on deep thinking. Until that explicit switch, the standing "no in-call failover for get_guidance" decision remains in force; do not switch it silently.

D5 — Dropped StageThresholdProcessor

Python wires it only for tool-call variants — its <system_instruction> reminder exists to nudge the LLM into calling update_stage, and its Sentry/tagging alarm detects that tool call failing to happen. With the tracker default there is nothing to remind or alarm on; transition failure modes are covered by the tracker's own Sentry paths (invalid output, config errors). No new core processor is needed for this port.

Net new shared surfaces: two in core, one in the router. ReplaceSystemMessage (D1) and OnLLMCallCompleted (D3) in voicepipelinecore; the hedged one-shot execution mode (D4) in llmrouter, which is already the sanctioned home for HTTP/provider machinery. Everything else — tracker, fuzzy matcher, StageManager, DeepThinking, CarePlan, config, state, resume, S3 state upload, new API methods, debug chunks — lives in disha/, using surfaces that already exist (Redis client, API client, DocumentStore, Jinja renderer, S3 uploader, UIEvents, CallEvents, the static end_call tool).

Sequenced so each phase builds and tests green (go test -race ./...) before the next; behavior is exercisable end-to-end from phase 3 onward via the local browser client with a real variant config. No commits without explicit review, per project rules.
