vago vs pipecat: pipeline structure, frame movement & how the call ends

Comparison of the Go voice pipeline (voicepipelinecore) against pipecat 0.0.108, focused on frame-processor topology, frame directions/ordering, and teardown semantics — and where we still diverge in ways that matter.

Scope: processor.go, pipeline.go, pipeline_edges.go, playback_sink_processor.go, tts_processor.go, the split UserContextAggregator/AssistantContextAggregator pair, and the assembled pipelines in disha/followup_call.go & disha/sales_call.go. pipecat references are to the installed 0.0.108 source.

TL;DR

The goodbye-commit path is now structurally sound and matches pipecat's safety model

Three things together make the final spoken turn commit before teardown, race-free by construction: (1) processors no longer self-cancel when an EndFrame passes through; (2) cleanup is global and only runs after the EndFrame reaches the sink; (3) the assistant aggregator sits at the tail and commits on a downstream signal (BotStoppedSpeaking) that is ordered ahead of the EndFrame on the same FIFO path. It also keeps our requirement that we commit the actually-played words, not generated text.

One place still has the original bug's shape: function-call handling travels upstream

Tool-call context (and its persisted chunks) is handled by UserContextAggregator above the LLM, fed by FunctionCall* frames that travel upstream — the opposite direction from the EndFrame. It is currently safe only by a large timing margin (1 hop up vs. a long downstream path through TTS+playback), not by ordering. It also opens a "re-run during shutdown" hazard for any future RunLLM=true tool used near end-of-call. Pipecat instead handles tool calls in the tail assistant aggregator (downstream). Relocating ours is the change to prioritize.

1. Pipeline structure

The split aggregator pair over one shared, mutex-guarded message list is a faithful port of pipecat's LLMContextAggregatorPair sharing one LLMContext. The assistant aggregator sits at the tail (after playback, before sink) — the same slot pipecat uses (after transport.output).

vago — disha/followup_call.go:162

source → audioSource → stt → userIdle → User() → llm → tts → playback → Assistant() → sink

sales_call.go is identical with a talkTime stage between User() and llm.

pipecat — 0.0.108

transport.input → user_agg → … → llm → tts → transport.output → assistant_agg

Same shape: user aggregator above the LLM, assistant aggregator at the tail after the output stage.

Frame-propagation mechanics also match: each processor has a priority input (system frames jump the queue) plus an in-order process queue. EndFrame is IsSystem=false (in-order) and IsInterruptible=false — the equivalent of pipecat's ControlFrame + UninterruptibleFrame on EndFrame (frames.py: EndFrame ≈ line 1877).

2. How the call ends — and why the commit is race-free now

The earlier teardown race is gone because the design changed in two compounding ways that together reproduce pipecat's guarantee.

2a. Processors no longer self-cancel on EndFrame

The base processLoop used to cancel the per-processor context and return the moment it processed an EndFrame. That is removed — processors stay alive until a single global Pipeline.Stop(), which only runs after the EndFrame reaches the sink (PipelineSink → CompleteEnd → runCleanup → Pipeline.Stop). This mirrors pipecat exactly: a base FrameProcessor has no EndFrame branch that stops itself; the PipelineTask drains to the sink and then cleans up globally (frame_processor.py process_frame; task.py _process_push_queue / _wait_for_pipeline_end).

// processor.go — processLoop, AFTER the fix (self-cancel removed)
case env := <-b.procCh:
    b.self.ProcessFrame(ctx, env.Frame, env.Direction)
    // (previously: if EndFrame { b.cancel(); return } — gone)

TTS needed a matching tweak: when it forwards the deferred EndFrame it now calls closeTTSConnection() (close the Cartesia socket only) instead of Stop(), so the TTS processor stays alive as a conduit for any upstream frames while the output side drains.

2b. The commit rides the same downstream path as the EndFrame

For a goodbye that ends the call, playback processes its queue in order and emits, all downstream to the tail Assistant() aggregator:

// playback_sink_processor.go — tick(), in queue order
played WordTimestampFrame → Downstream   // words, as audio actually plays
TTSDoneFrame           → Downstream
Broadcast(BotStoppedSpeakingFrame)        // downstream copy = commit trigger
EndFrame               → Downstream   // drained AFTER the audio

So Assistant() receives, in order: played words → BotStoppedSpeaking (commit the played turn) → EndFrame (flush backstop, no-op if already committed) → on to sink (which triggers cleanup). The commit is strictly ahead of the sink on a single FIFO path through one processor — no up-vs-down divergence, so no race. This is the same property pipecat relies on, and it preserves our reconciliation requirement: the committed text is the actually-played words.

Why this is immune to teardown by construction

The commit is a synchronous mutation of shared state triggered by frames that always reach the tail downstream-in-order; the EndFrame is uninterruptible and ordered behind them; and the dispatcher that persists the chunk is drained during cleanup (callEvents.stopAndDrain()) which runs after the EndFrame passed Assistant(). Pipecat's commit has the identical property (local add_message first, frames pushed after).

4. Significant divergence: function-call handling goes the opposite direction from pipecat

This is the one to flag hardest, because it is the same shape as the original goodbye-loss bug.

In pipecat the tail assistant aggregator owns all assistant context — text and tool calls — and only pushes context upstream to re-run the LLM. In vago it is split:

  • Assistant() (tail) commits the spoken text from downstream played-word frames.
  • UserContextAggregator (above the LLM) handles tool calls; FunctionCallInProgress/FunctionCallResult travel upstream (user_context_aggregator.go:264, 271), and the tool-call context mutation + fireToolResultCommitted (chunk persist) depend on those upstream frames.

Why it's safe today — but not by construction

The upstream FunctionCall* frames are 1 hop (llm → User), while the EndFrame that triggers cleanup is many hops down plus the TTS synthesis wait plus the playback drain. So the tool messages commit with a huge margin before cleanup. It works because of that hop-count asymmetry, not because anything orders the two — exactly the fragile situation we just removed from the spoken-turn commit.

Related hazard: re-run during shutdown

Because FunctionCall* frames are unordered relative to the downstream EndFrame, a FunctionCallResult with RunLLM=true arriving at User() after the EndFrame has passed would push a fresh LLMMessagesFrame downstream and start another LLM turn during shutdown. end_call is safe only because its result is RunLLM=false; any future re-running tool used near end-of-call reopens this.

Clean fix (full pipecat parity): move function-call handling into the tail Assistant() aggregator so those frames flow downstream, in-order with everything else, and have Assistant() push the re-run context upstream (as pipecat does). That collapses the last opposite-direction commit path and removes the shutdown re-run hazard.

5. Other divergences worth knowing

Interruption is downstream-only, not a broadcast

vago's barge-in InterruptFrame is a system frame pushed downstream only (user_context_aggregator.go:284); pipecat broadcasts it both ways (frame_processor.py broadcast_interruption). Downstream reaches llm/tts/playback/Assistant (cancels generation, flushes played words — good), but stt/userIdle above User() never see it. Likely fine (they don't need it), but upstream-side state can't react to a barge-in, which is a behavioral gap vs pipecat.

Commit trigger = BotStopped (played), not LLMFullResponseEnd (generated)

Deliberate and correct for our reconciliation requirement — but note it matches pipecat's deprecated aggregator (commit on BotStoppedSpeaking), not the current universal one (commit generated text on LLMFullResponseEnd). Consequence: on barge-in the InterruptFrame is a system frame and can jump ahead of the last one or two played WordTimestamps still queued in Assistant(), so the committed barge-in text may be very slightly short. Pipecat's interruption has the same race, so it's consistent — just be aware "played words on interrupt" is best-effort to the last frame.

End vs Cancel are one frame with a reason, not two frame types

pipecat separates graceful EndFrame (drain) from CancelFrame (immediate drop, short-circuits queues). vago overloads EndFrame + shouldStopPlaybackImmediately(reason) at the playback sink (client-disconnect/error ⇒ drop audio, else drain). Functional, but "immediate teardown" is not a first-class, pipeline-wide concept the way pipecat's CancelFrame is — only playback honors the immediacy.

Minor: dead TTSDoneFrame branch in the user aggregator

UserContextAggregator still has a TTSDoneFrame case (user_context_aggregator.go:302), but playback no longer sends TTSDone upstream (it's downstream now), so that branch is unreachable. Back-channel discard now correctly rides the upstream BotStoppedSpeaking broadcast copy instead. Harmless, worth cleaning up.

7. Bottom line

The spoken-turn / goodbye-commit path now matches pipecat's safety model — no self-cancel, drain-to-sink-then-cleanup, commit on a downstream signal ordered ahead of the EndFrame — while keeping played-word reconciliation, which pipecat doesn't do. That class of bug is closed for the assistant text.

The single remaining place with the original bug's shape is function-call handling, which travels upstream into the UserContextAggregator: currently safe by timing margin rather than by construction, and the source of a latent "re-run during shutdown" hazard for any RunLLM=true tool near end-of-call. Relocating tool-call handling to the tail Assistant() aggregator (downstream, like pipecat) is the change to prioritize if we want full parity and to retire the class of issue entirely. The rest — downstream-only interrupt, End/Cancel overloading, the dead TTSDone branch — are minor and behaviorally acceptable today.
